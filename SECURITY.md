# Security

Shastra Connect holds children's personal data, marks, attendance and payments. Security is designed in at every
layer, and the API's integration tests check the controls below (`npm test`).

## Controls

### Identity & sessions
- **Staff** sign in with email + password, hashed with **Argon2id** (m = 19 MiB, t = 2, p = 1). The password policy
  requires at least 10 characters, letters and digits, and blocks common passwords.
- **Parents and students** sign in with a **6-digit WhatsApp code**:
  - generated by a CSPRNG and stored only as an HMAC
  - expires after 5 minutes, allows 5 attempts and is single-use
  - limited to one code every 60 s and 5 codes an hour per number
  - the response is identical whether or not the number is registered, so numbers cannot be enumerated
- **Brute force:** an account locks for 15 minutes after 5 failures, and login, OTP and payment endpoints are
  rate-limited per IP. Error messages are generic and timing is equalised with a dummy hash.
- **Sessions** are opaque 256-bit tokens. Only a SHA-256 of each token is stored. The cookie is
  `__Host-sc_sid`, which means `HttpOnly; Secure; SameSite=Lax; Path=/` with no Domain.
  - Staff sessions expire after 12 hours, family sessions after 30 days.
  - Each user can have at most 10 sessions.
  - Signing in rotates the session (blocking fixation), and logout destroys it on the server.
  - Changing a password signs out every other device. "Sign out everywhere" is also available.

### Request integrity
- **CSRF:** every unsafe request must pass the same-origin `Origin` / `Sec-Fetch-Site` check and carry the
  per-session `X-CSRF-Token`, compared in constant time.
- **Validation:** every input goes through strict zod schemas. Unknown fields are rejected, which prevents
  mass-assignment.
- **SQL injection:** all SQL is parameterised. The only dynamic column names come from fixed allow-lists.
- **Size limits:** JSON bodies are capped at 1 MB, uploads at 15 MB, and every list endpoint caps how many rows it returns.

### Authorisation
- **Role checks** run on every route.
- **Object-level checks** run on every record id: a parent can only reach their own children, and a teacher only
  their assigned sections and subjects. Tests cover this for students, fees, attendance, analytics and files.
- Families see marks and answer sheets only after results are published.

### Files
- The upload type is decided by the file's **magic bytes**, never its name or MIME type. Only PDF, DOCX, PNG, JPG
  and WEBP are accepted.
- Files are stored outside the web root under random UUID names.
- Downloads go only through `/api/files/:id`, which runs an authorisation check and sends
  `Content-Disposition`, `nosniff`, `CSP: sandbox` and `Cache-Control: private, no-store`.

### Payments
- The amount is computed on the server from locked fee balances.
- Payment verification uses Razorpay's HMAC signatures, for both the checkout callback and the webhook.
- The webhook checks that the amount matches before marking a payment as paid.
- Finalising a payment is idempotent.
- Receipt numbers are sequential and every payment is audited.
- The **mock** gateway is refused in production.

### Webhooks
- WhatsApp webhooks are checked with `X-Hub-Signature-256` (an HMAC over the raw body, constant-time compare).
- Razorpay webhooks are checked with `X-Razorpay-Signature`.
- Webhooks never use cookies.

### Browser hardening
- **API responses:** `default-src 'none'` CSP, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer` and `no-store`.
- **App pages (served by Caddy):** strict CSP where Razorpay checkout is the only third-party origin, HSTS
  (2 years, preload), COOP, `X-Frame-Options: DENY` and a restrictive Permissions-Policy.
- Fonts are self-hosted, so there is no third-party CDN.

### Privacy
- Logs redact cookies, authorisation headers, passwords and OTPs, and phone numbers are masked.
- OTP payloads are wiped from the outbox after sending.
- The WhatsApp log masks recipient numbers.
- Birthday data is visible to the Principal and Office only.

### Audit
An append-only `audit_logs` table records:
- sign-ins, failures and lockouts
- password and staff changes
- attendance, marks, results publication and uploads
- fee items, payments and reminders
- notices and events

The Principal can view it in the app.

### Configuration
- The environment is validated at boot.
- In production the app refuses to start with placeholder secrets, a non-HTTPS origin, the mock payment provider,
  or missing WhatsApp/Razorpay secrets.

### Database
- Postgres uses a least-privilege app role: not a superuser, and unable to create databases or roles.
- `scram-sha-256` authentication and data checksums are enabled.
- In production the database sits on an internal Docker network with no internet access and no published port.
  In development it is bound to 127.0.0.1 only.

### Containers
- Containers run as a non-root user with a read-only root filesystem.
- `cap_drop: ALL` and `no-new-privileges` are set, and tini is PID 1.
- The worker is separate from the API.
- Only Caddy (ports 80 and 443) is exposed.

### Supply chain
- `.npmrc` sets `ignore-scripts=true` and `save-exact=true`, and the lockfile is committed.
- CI runs `npm audit --omit=dev --audit-level=high`.
- Dependabot updates npm packages, Docker images and GitHub Actions.

### Backups
- A nightly `pg_dump` is kept for 14 days. See `docs/OPERATIONS.md` for off-site copies.

## Before going live — checklist

Run `npm run preflight -- --online` first. It checks every item it can automatically.

- [ ] Fresh `SESSION_SECRET`, `DB_APP_PASSWORD` and `POSTGRES_SUPERUSER_PASSWORD`, each from a CSPRNG.
- [ ] `.env` is `chmod 600` and never committed.
- [ ] `DOMAIN` points at the server, so Caddy can obtain the certificate.
- [ ] Firewall: allow 22 (SSH key only), 80 and 443; deny everything else.
- [ ] Razorpay live keys are set and the webhook URL `https://DOMAIN/api/webhooks/razorpay` is configured with its secret.
- [ ] The WhatsApp Business number is verified, the templates in `docs/WHATSAPP.md` are approved, and the webhook is
      configured with the verify token and app secret.
- [ ] The demo seed has **not** been run (it refuses in production). Create the first principal with
      `npm run create-principal` (see README).
- [ ] Backups are copied off the server, and a restore has been tested once.
- [ ] Parents have been told that school staff will never ask for their login code.

## Reporting a vulnerability

Please email the maintainer privately rather than opening a public issue. Include the steps to reproduce.
